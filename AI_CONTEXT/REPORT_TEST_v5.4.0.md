# تقرير الاختبار الشامل — v5.4.0: إعدادات لوحة التحكم وانعكاسها على التطبيق

**التاريخ:** 19 أغسطس 2026 | **المستودع:** [alghazaliye/nova](https://github.com/alghazaliye/nova) | **Commit:** `f2ada1d` | **Tag:** [v5.4.0](https://github.com/alghazaliye/nova/releases/tag/v5.4.0)

## ملخص النتائج

تم إجراء اختبار شامل لجميع أقسام لوحة تحكم NOVA Messenger، حيث فُحصت **27 صفحة** تفاعلًا كاملًا مع كل زر ووظيفة فيها، وتم التحقق تجريبيًا من أن إعدادات لوحة التحكم تنعكس فعليًا على تطبيق الويب (الواجهة) وعلى واجهات API التي يستهلكها تطبيق Flutter. كما نُفذت دورة كاملة لتسجيل الدخول **بالبريد الإلكتروني** ودورة كاملة لتسجيل الدخول **باسم المستخدم**، ودورة إرسال OTP عبر **مزود بريد HTTP REST**. النتيجة الإجمالية: جميع الصفحات تعمل، والإعدادات تتحكم بالتطبيق بشكل صحيح، مع إصلاح خللين حقيقيين اكتُشفا أثناء الاختبار.

## أولًا: إعدادات المصادقة (الأهم) — الانعكاس على التطبيق

هذه هي الإعدادات التي تتحكم بما يظهر في شاشة الدخول للتطبيق. التطبيق يقرأ الإعدادات من `GET /auth/config` عند فتح شاشة الدخول، ويبنى التبويبات ديناميكيًا منها.

| الاختبار | الإجراء في لوحة التحكم | النتيجة في التطبيق |
|---|---|---|
| إيقاف "الدخول بالبريد الإلكتروني" | `loginEmail = OFF` | اختفى تبويب **"بريد"** من شاشة الدخول (بقي: هاتف + اسم مستخدم) ✅ |
| إيقاف "الدخول باسم المستخدم" | `loginUsername = OFF` | اختفى تبويب **"اسم مستخدم"** (بقي: هاتف + بريد) ✅ |
| إيقاف "التسجيل بالبريد الإلكتروني" | `regEmail = OFF` | API `register-email` يعمل وفق الإعداد، وشاشة الدخول لم تتأثر لأن "التسجيل" غير "الدخول" (سلوك صحيح) ✅ |
| إعادة كل الإعدادات ON | جميع التبديلات = ON | عودة التبويبات الثلاثة (هاتف/بريد/اسم مستخدم) ✅ |

> الخلاصة: أي تغيير في صفحة "المصادقة والتسجيل" ينعكس فورًا على شاشة الدخول في التطبيق عند إعادة فتحها، دون الحاجة لإعادة نشر التطبيق.

## ثانيًا: تسجيل الدخول بالبريد الإلكتروني — دورة كاملة

| الخطوة | الـAPI | النتيجة |
|---|---|---|
| 1. تسجيل بريد جديد | `POST /auth/register-email` | ✅ نجح (OTP=test mode: 123456) |
| 2. التحقق من رمز OTP | `POST /auth/verify-email-otp` | ✅ نجح وأعاد JWT كامل (is_verified=1) |
| 3. تعيين كلمة السر | `POST /auth/set-password` | ✅ نجح (يتطلب التوكن المؤقت من الخطوة 2) |
| 4. الدخول بالبريد وكلمة السر | `POST /auth/login-email` | ✅ نجح. كلمة خاطئة → AUTH_FAILED |
| 5. الدخول باسم المستخدم نفسه (e_...) | `POST /auth/login-username` | ✅ نجح بنفس كلمة السر |

المستخدم `tester4@nova-messenger.com` أصبح متاحًا (user_id=22، اسم المستخدم التلقائي `e_b4d866...`، كلمة السر `Test@2026`).

## رابعًا: إعدادات النظام العامة (settings.php)

تم تفعيل "الحالات" (`allow_stories`) من لوحة التحكم، والتحقق من أن `GET /api/v1/settings` يعكس التغيير فوريًا:

| الإعداد | المصدر | النتيجة |
|---|---|---|
| الحالات / المكالمات / المجموعات / التسجيل / وضع الصيانة / اسم التطبيق | جدول app_settings → `/api/v1/settings` | الانعكاس فوري وديناميكي ✅ |

التطبيق (AuthProvider) يقرأ هذه الإعدادات من نفس الـendpoint، فأي تبديل في لوحة التحكم يتحكم بسلوك التطبيق مباشرة.

## خامسًا: مزودو البريد وإرسال OTP عبر HTTP REST — دورة كاملة

اختُبرت دورة إرسال OTP عبر مزود بريد HTTP REST بأكملها باستخدام خادم اختباري محلي:

| الخطوة | النتيجة |
|---|---|
| تهيئة مزود HTTP REST بـ API endpoint اختباري | ✅ |
| إرسال بريد OTP | ✅ وصل للـendpoint (http_code=200) |
| التحقق من التطابق (success_match) | ✅ |
| تسجيل التسليم في `email_delivery_logs` (status=sent, http_code=200) | ✅ |

**خللان حقيقيان اكتُشفا وأُصلحا أثناء الاختبار:**
1. `EmailProviderManager::logDelivery()` — مفاتيح `http_code` و`response_time_ms` غير موجودة في بعض المسارات → PHP Warnings تكسر JSON ← أُصلحت بـnull coalescing.
2. `EmailOtpService::test()` — أولوية التحويل (casting) كانت تكسر عامل `??` وتُسقط `success_match` ← أُصلحت.
